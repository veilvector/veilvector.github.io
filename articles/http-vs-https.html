HTTP vs HTTPS

Your browser has found a destination. Now it needs to communicate with the server — and that conversation needs rules and protection.

01 / Picking up the trail

Finding a server is only the beginning

In the previous guides, we explored domain names, DNS, IP addresses, and ports. Each concept helps explain another part of how a browser reaches a web service.

Imagine we're back at that moment. Your browser has a destination in mind, and now it needs to ask for something — perhaps a webpage, an image, or some data.

A simplified web journey
01 Browser

You request a website.

→
02 Destination

DNS and network routing help reach the service.

→
03 Web server

The server receives and handles the request.

This is a simplified overview. DNS resolution and connection setup involve additional steps that may vary with caching and protocol.

Your browser and the server need a common way to describe requests and responses. That is where HTTP enters the story.

02 / The conversation

So, what is HTTP?

HTTP stands for Hypertext Transfer Protocol. It defines how a client, such as your browser, sends requests and receives responses from a server.

The basic idea is straightforward: the browser asks for a resource, and the server returns a response. The response might contain the requested content, or it might explain why the request could not be fulfilled.

Request and response
SEND Browser

Requests a resource

→
HANDLE Server

Processes the request

→
RETURN Browser

Receives the response

Your browser handles this exchange behind the scenes. You don't have to manually write requests every time you visit a page.

03 / Under the surface

What does a request look like?

When you enter a URL and press Enter, your browser may send a request similar to this one. It asks for the resource at /index.html.

Example HTTP request · HTTP/1.1
GET /index.html HTTP/1.1
Host: example.com

The server can respond with a status line and the requested content. A simplified successful response might look like this:

Example HTTP response · HTTP/1.1
HTTP/1.1 200 OK
Content-Type: text/html

<html>
  ...
</html>

These are illustrative HTTP/1.1 examples, not a complete exchange. Other HTTP versions use different on-the-wire formats.

04 / When things go wrong

Not every response means success

A server doesn't always return the page you requested. Perhaps the resource doesn't exist, or the server encountered a problem. HTTP status codes help describe the result.

200
OK — the request succeeded.
404
Not Found — the requested resource wasn't found.
500
Internal Server Error — the server encountered an unexpected condition.

For developers and security analysts, status codes are useful clues. In logs, they can help reveal errors, unusual request patterns, or repeated attempts to access unavailable resources. A status code alone, however, rarely tells the whole story.

05 / The security problem

What if someone could read the conversation?

Imagine sending a letter that reaches its destination, but someone along the way can read or alter its contents. The communication worked — but it wasn't private or protected from interference.

Plain HTTP does not itself provide TLS encryption for the connection. Depending on the network and circumstances, traffic may be exposed to interception or modification.

Think about it

Would you want your password travelling across a network in a form an observer could simply read?

This is one reason HTTPS matters.

06 / Adding protection

HTTPS protects the conversation

HTTPS means HTTP over TLS — Transport Layer Security. TLS helps protect the communication between a browser and a server.

CONFIDENTIALITY

Encryption helps prevent network observers from simply reading the protected contents of the connection.

INTEGRITY

TLS helps detect unauthorised changes to protected data while it is being transmitted.

AUTHENTICATION

Certificate validation helps the browser verify the identity associated with the server it intended to reach.

The exact details depend on the TLS version and configuration, but the core idea is that HTTPS adds protection to web communication.

HTTPS doesn't change the purpose of the conversation. It adds a protected way for that conversation to happen.
07 / Comparing the two

HTTP and HTTPS aren't two unrelated protocols

Both are used for communication between web clients and servers. The important distinction is whether the connection uses TLS protection.

HTTP
HTTPS
Web communication without TLS protection.
HTTP communication protected by TLS.
Commonly associated with port 80.
Commonly associated with port 443.
Does not itself provide TLS confidentiality or integrity.
TLS provides confidentiality and integrity for the connection.

Ports 80 and 443 are the conventional defaults, not unbreakable rules. Services can be configured to use other ports.

One important detail: HTTPS does not automatically mean a website is trustworthy.

08 / A common misconception

Does the padlock mean a website is safe?

It's tempting to treat a browser's security indicator as a guarantee that a website is legitimate. But HTTPS is not a judgement about the site's intentions.

A phishing website can use HTTPS, too. Its connection may be encrypted even while the site is trying to steal credentials.

Make the distinction

If a suspicious login page uses HTTPS, should you automatically trust it?

No. Check the domain carefully, consider how you reached the page, and look for other warning signs. HTTPS helps protect the connection; it does not prove that a website is honest or harmless.

09 / The investigator's view

Follow the clues in a real incident

Imagine a user reports clicking a link in an email and entering their password. The investigation shouldn't stop at whether the page used HTTPS.

Useful questions include:

DOMAIN

Which domain did the link point to, and did it resemble a legitimate service?

DNS / IP

What destination information was observed, and when did the connection occur?

WEB REQUESTS

What requests were made, and what responses followed?

AFTERWARD

Were there suspicious sign-ins or other activity after the credentials were submitted?

These clues connect networking concepts to web traffic analysis and incident response. A single clue rarely proves what happened; investigators build a timeline from multiple sources.

Domain → DNS → IP address → Port → HTTP/HTTPS → Request and response
The takeaway

Understand the conversation — and its protection

HTTP defines how browsers and web servers exchange requests and responses. HTTPS uses TLS to help protect that communication through encryption, integrity protection, and server authentication.

But a protected connection is not the same as a trustworthy website. In cybersecurity, the surrounding evidence still matters.
