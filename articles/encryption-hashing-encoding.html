Encryption, Hashing & Encoding

They can all make information look completely different. But they solve very different problems. The trick is to understand what happened to the data and why.

Guide 013 · Cryptography fundamentals
01 — The original message

Something changed

Imagine finding a message in a system's logs. The original message is easy to understand:

The original message · Plain data

Meet me at 8 PM.

Readable information in its original form.

But somewhere else, you find a string that looks completely different. Has the information been encrypted? Has it been hashed? Or has it simply been encoded into another format?

All three can change how data looks. Their purposes, however, are not the same.

02 — First clue

Encryption: protect the information

Encryption is about protecting information from unauthorized access. It transforms readable data, called plaintext, into ciphertext using a cryptographic algorithm and key.

Follow the transformation
Before Plaintext

The original readable data

→
After Ciphertext

The encrypted data

Decryption uses the appropriate key and cryptographic process to recover the original information.

Imagine sending sensitive information across a network. Without suitable encryption, someone who obtains the transmitted data may be able to read it. Properly implemented encryption helps protect its confidentiality.

The key matters: access to the right key and a suitable decryption process allows an authorized party to recover the information.

Think protection. Encryption is designed to keep information confidential from parties who do not have the necessary key or access.

HTTPS, encrypted messaging, and encrypted storage are examples of systems that use cryptography to protect information. Their security depends on how the cryptography and the surrounding system are implemented.

03 — Second clue

Hashing: create a digest

Hashing solves a different problem. A hash function takes input data and produces an output called a hash value or digest.

A cryptographic hash function produces a fixed-length digest for a given algorithm, regardless of the input's size.

Follow the transformation
Input Original data

Text, a document, or another file

→
Output Fixed-length digest

A value produced by the hash function

A cryptographic hash is designed to make it computationally infeasible to reconstruct the original input from the digest alone. Hashing is not normally reversed using a decryption key.

Another useful property is that even a small change to the input should produce a substantially different digest with a well-designed cryptographic hash function.

Input A

Hello

Produces digest A.

Input B

hello

Produces a substantially different digest B.

The example illustrates the expected behaviour; the actual digest depends on the hash algorithm being used.

04 — Passwords and integrity

Where does hashing become useful?

Consider a website that stores user accounts. If it stores everyone's passwords as readable text, a database breach could expose those passwords directly.

A secure password-storage system instead uses a dedicated password-hashing algorithm to store a password verifier. During login, the system uses the entered password to perform the verification process.

A simplified login check
Step 1 Password entered

The user submits a password.

→
Step 2 Verify

The system checks it against the stored verifier.

Modern password storage should use an appropriate password-hashing algorithm, such as Argon2id, scrypt, or bcrypt, with salts and suitable work factors. Simply storing a fast general-purpose hash of a password is not sufficient protection.

Hashes are also useful when checking file integrity. If a trusted hash of a file is available, you can calculate the file's hash again and compare the results to check whether its contents have changed.

One important distinction: a matching hash can help establish that content matches a trusted reference. It does not, by itself, prove who created the file or whether the file is trustworthy.

05 — Third clue

Encoding: change the representation

Encoding changes how information is represented so that systems can store, transmit, or process it in an expected format. Encoding is not automatically a security measure.

One common example is Base64. It represents binary data using a set of printable characters.

The same text, a different representation
Original text

Hello

Base64 representation

SGVsbG8=

The encoded value can be decoded back to the original text without a secret cryptographic key.

Base64 may look unfamiliar, but anyone who knows the encoding can decode it. It does not make the information confidential.

REMEMBER THIS

If someone sends you a Base64 string, don't assume the data is encrypted just because it looks unreadable at first glance.

06 — Compare the clues

Same transformation, different purpose

The easiest way to distinguish the three is to ask what the transformation is meant to accomplish.

Encryption

Protects information. The appropriate decryption process and key can recover the original data.

Hashing

Produces a digest used for checking or verification. Cryptographic hashing is designed to be one-way.

Encoding

Represents data in another format. The corresponding decoding method can recover the original representation.

The key difference isn't how strange the output looks. It's the purpose of the transformation and how the system uses the result.

07 — Investigate the string

Now imagine you're investigating a system

You find a strange-looking string inside a log file, URL, configuration file, or application response. It might resemble encoded data, a hash, or ciphertext.

Your first instinct might be to declare, "That's encrypted." But the appearance of a string alone usually isn't enough to establish how it was produced.

Examine the evidence

  1. Format

    Could the string be encoded?

  2. Purpose

    Could it be a hash used for verification?

  3. Protection

    Is encryption actually being used?

  4. Source

    Which application or process produced it?

  5. Context

    What do nearby events, fields, or requests reveal?

Context matters. A string in a URL parameter might use URL encoding. A password verifier in a database may use a password-hashing format. Encrypted application data may appear as ciphertext.

These are clues, not guarantees. Investigate how the application handles the data before deciding what it means.

08 — The final clue

Ask what the system is trying to do

Before identifying an unfamiliar string, connect the transformation to its purpose.

Protect

Encryption helps keep information confidential.

Check

Hashing produces a digest for verification.

Represent

Encoding changes the data's representation.

PAUSE FOR A SECOND

You find the string SGVsbG8= in an application log. You discover that decoding it produces the text "Hello". Was the original text necessarily encrypted?

No. In this example, the string is a Base64 representation. It can be decoded without a secret key. The fact that data looks different does not establish that encryption was used.

THE TAKEAWAY

Encryption protects information, hashing creates a digest, and encoding changes data's representation. Encryption can be reversed with the appropriate key and process. Hashing is designed to be one-way, while encoding can be reversed using the corresponding decoding method.

When you encounter unfamiliar data during a cybersecurity investigation, don't guess from its appearance. Examine its format, source, purpose, and surrounding context.
